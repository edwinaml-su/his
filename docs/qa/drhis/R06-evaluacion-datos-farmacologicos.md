# Informe de hallazgos — R06 Datos farmacológicos provisionales (assessment Code Castle) — 2026-08-22

## Resumen ejecutivo

Evalué como médico prescriptor el motor de verificación de interacciones medicamentosas de `packages/trpc/src/routers/pharmacy.router.ts`, contra el catálogo real de medicamentos del hospital (BD de producción, solo lectura) y contra la pantalla que un clínico usaría. Hallazgo central, más grave que "el dataset es provisional": **el motor de interacciones no se ejecuta hoy sobre ningún medicamento real, y el camino por el que este hospital ordena medicamentos en la práctica (`ece.indicaciones_medicas`) no pasa por él ni podría — captura el fármaco como texto libre, sin identidad clínica estructurada.** El dataset de 50 pares (Wave 1, mayo 2026) es, además, insuficiente frente al formulario real: 12 de 13 fármacos de alto riesgo (ISMP) que el hospital sí dispensa hoy —digoxina, fentanilo, cloruro de potasio, metotrexato, vancomicina, quetiapina, tacrolimus, entre otros— no tienen ni una sola regla de interacción. 6 hallazgos: 2 Críticos, 3 Altos, 1 Medio. **No recomiendo poner en producción el módulo de prescripción electrónica con verificación de interacciones tal como está** — no porque el dataset sea chico, sino porque el control de seguridad, aunque bien diseñado en el código, es inalcanzable desde la práctica clínica real del hospital.

## Alcance y método

- **Evaluado:** `packages/trpc/src/routers/pharmacy.router.ts` (mecanismo de interacciones al firmar receta), `packages/contracts/src/schemas/pharmacy.ts` (helpers puros), `packages/database/seed/drug-interactions.json` (dataset Wave 1), el modelo `Drug`/`CatalogoMedicamento` en `packages/database/prisma/schema.prisma`, las pantallas `apps/web/src/app/(clinical)/pharmacy/*`, y el flujo NTEC de indicaciones médicas (`ece.indicaciones_medicas` / `ece.indicacion_item`).
- **Ambiente:** producción (Supabase `ejacvsgbewcerxtjtwto`), acceso de **solo lectura** vía `psql` con `DIRECT_URL`. No modifiqué código ni datos.
- **Escenario base:** un médico prescribe warfarina + un AINE a un paciente hospitalizado; en paralelo, verifico si un médico que ordena digoxina, fentanilo o metotrexato —fármacos de alto riesgo que el hospital sí compra y dispensa— recibe alguna alerta.
- **Qué NO evalué:** no recorrí la pantalla con sesión real logueada (ver "No verificado" — el catálogo `Drug` vacío en el único ambiente disponible impide un flujo de punta a punta con datos reales; usé lectura de código + BD, que el protocolo del rol acepta como evidencia cuando la UI no es ejercitable). No evalué el módulo de alergias del paciente (fuera del alcance de R06). No inspeccioné los 227 SQL numerados en busca de un backfill de `Drug`/`CatalogoMedicamento` pendiente de aplicar — solo confirmé el estado actual en prod.

## Hallazgos

### H-01 · El motor de interacciones no está conectado al camino real por el que este hospital ordena medicamentos · **Crítico**

- **Proceso/módulo:** Indicaciones médicas NTEC (`ece.indicaciones_medicas` / `ece.indicacion_item`) vs. módulo de Farmacia (`pharmacy.router.ts`).
- **Qué observé:** `ece.indicacion_item` —la tabla real donde un médico registra "MEDICAMENTO" dentro de una indicación médica, y de la que cuelga la administración por enfermería (`ece.administracion_medicamento` referencia `indicacion_item_id`)— almacena el fármaco como **texto libre** (`descripcion text`, `dosis text`, `via text`). No tiene `drugId`, no tiene `atcCode`, no tiene ninguna columna que enlace con `Drug` ni con `CatalogoMedicamento`. Confirmé por grep en todo `apps/web/src/app/(clinical)/ece/` que ninguna pantalla de ese árbol referencia `drugId`, `atcCode` ni `CatalogoMedicamento`. El helper `detectInteractionAlerts` (el único punto del código que consulta el dataset de interacciones) solo se invoca desde `pharmacy.router.ts` — ningún otro router del proyecto lo llama.
- **Consecuencia:** cuando un médico de este hospital ordena "Warfarina 5mg VO cada 24h" dentro de una indicación médica (el flujo NTEC que sí está en uso), el sistema no tiene forma de saber que ese texto es warfarina en sentido farmacológico — no hay verificación de interacción posible, ni aunque el dataset tuviera 10,000 pares. El motor de interacciones evaluado por R06 protege un módulo (`pharmacy.prescription`) que no es el que produce las órdenes médicas reales de este hospital.
- **Norma aplicable:** `TDR_HIS_Multipais.md` §15.3 exige "validación clínica en tiempo real: interacciones medicamento-medicamento... con base de conocimiento integrada" como parte del módulo de farmacia — no distingue two rutas de prescripción, exige que **la** ruta de prescripción la tenga. Ley de Deberes y Derechos de los Pacientes: registro veraz y seguro del acto de prescribir (norma aplicable, artículo por confirmar con asesoría legal).
- **Naturaleza:** defecto de diseño — dos módulos de prescripción independientes que no se hablan entre sí, no un catálogo incompleto.
- **Recomendación:** antes de invertir en licenciar una fuente farmacológica comercial, decidir **cuál es la única ruta de prescripción** de este hospital (indicaciones médicas NTEC, ya en uso, o el módulo Farmacia con state machine DRAFT→SIGNED→DISPENSED). Consolidar en una — la regla de "adecuar legacy, no duplicar" del proyecto aplica aquí tanto como a cualquier otro dominio clínico. Cualquier motor de interacciones que se licencie debe cablearse a la ruta que gane, con `drugId`/`atcCode` estructurado en el punto de captura.
- **Evidencia:** `packages/database/prisma/sql` — `\d ece.indicacion_item` (columnas `descripcion text`, sin FK a `Drug`); grep `drugId|atcCode|CatalogoMedicamento` sobre `apps/web/src/app/(clinical)/ece/` → 0 resultados; grep `detectInteractionAlerts` sobre `packages/` y `apps/` → único call site en `pharmacy.router.ts:311`.

### H-02 · El hard-stop de interacciones nunca se dispara en la práctica: ninguna pantalla llama a `prescription.sign` · **Crítico**

- **Proceso/módulo:** `/pharmacy/new` (crear receta) → `pharmacy.prescription.sign` (firma + verificación de interacciones).
- **Qué observé:** `pharmacy.router.ts` implementa correctamente, a nivel de procedimiento tRPC, un hard-stop: al firmar (`prescription.sign`), si hay interacción `major`/`contraindicated` sin `forceOverrideJustification`, lanza `PRECONDITION_FAILED` y no permite avanzar. El estado por defecto de `Prescription` es `DRAFT` (schema.prisma línea 2118) y `prescription.create` no lo cambia. Busqué en todo `apps/web` una llamada a `.sign` sobre el router de farmacia: **no existe ninguna**. `/pharmacy/new/page.tsx` solo invoca `pharmacy.prescription.create.useMutation` y redirige a `/pharmacy`; no hay botón "firmar receta" en ninguna pantalla. Como `dispense.create` exige `status IN ('SIGNED','PARTIALLY_DISPENSED')`, una receta creada desde la pantalla real del hospital queda huérfana en `DRAFT` — ni se verifica interacción, ni se puede dispensar — salvo que alguien la firme por fuera de la UI (Postman, script). Confirmé en BD de producción: `Prescription` = 0 filas, `PrescriptionItem` = 0 filas, `Drug` = 0 filas — el módulo nunca operó con datos reales.
- **Consecuencia:** el comentario del propio archivo dice "interaction checks al firmar... bloquea si major/contraindicated salvo override" — eso es cierto del código, pero **falso del sistema que un médico usa**. Un evaluador o auditor que solo lea el código o los tests concluiría que hay un hard-stop funcionando; un médico que use la pantalla real nunca lo ve, nunca lo dispara, y nunca sabe que existió una alerta. Es exactamente el patrón de incidente que ya pagó este proyecto con los resultados críticos de laboratorio (IPSG.2): pantalla y router completos, circuito nunca cerrado.
- **Norma aplicable:** JCI MMU (Medication Management and Use) exige un sistema de revisión de la prescripción antes de la dispensación, incluyendo el cribado de interacciones significativas — el estándar exacto (edición 7ª vs. 8ª, vigente para la certificación que persiga Avante) debe confirmarse con el área de calidad; no cité artículo porque no verifiqué cuál edición aplica contractualmente.
- **Naturaleza:** defecto del sistema (brecha de integración UI↔backend), no falta de configuración.
- **Recomendación:** cablear un paso de firma explícito en la UI de farmacia (o decidir, junto con H-01, que este módulo se retira en favor de indicaciones médicas) antes de considerar cerrado ningún trabajo sobre el dataset de interacciones. Verificar con Playwright un test que efectivamente dispare el hard-stop desde la pantalla, no solo contra el router mockeado.
- **Evidencia:** `apps/web/src/app/(clinical)/pharmacy/new/page.tsx` (sin referencia a `.sign`); grep `prescription.*sign` sobre `apps/web` → 0 coincidencias relevantes; `SELECT count(*) FROM "Prescription"` = 0, `SELECT count(*) FROM "Drug"` = 0 (producción, 2026-08-22).

### H-03 · El dataset no cubre los fármacos de alto riesgo que el hospital sí dispensa hoy · **Alto**

- **Proceso/módulo:** `packages/database/seed/drug-interactions.json`.
- **Qué observé:** el dataset tiene 50 pares / 38 códigos ATC / severidades `major` (20), `moderate` (27), `minor` (3) — nunca usa el nivel `contraindicated` que el propio motor soporta. Crucé los 37 nombres genéricos mencionados en las descripciones del dataset contra el catálogo real de productos que el hospital factura (`ServicePriceListItem`, categoría MEDICAMENTOS/MEDICAMENTOS CONTROLADOS, 1,897 códigos distintos, 61 listas de precio activas — importado de Odoo): 34/37 (92%) sí corresponden a productos que el hospital vende. El criterio clínico de lo que **sí** está no es malo. El problema es lo que falta: crucé 13 fármacos de alerta alta (ISMP) contra el mismo catálogo real —
  digoxina, fentanilo (fentanil), cloruro de potasio, metotrexato, vancomicina, quetiapina, tacrolimus, sertralina, pregabalina, oxicodona, ceftriaxona, clindamicina, metronidazol— y **12 de 13 se venden en el hospital y ninguno tiene una sola regla de interacción** en el dataset (metronidazol es la única excepción parcial, tampoco cubierto pero interactúa con warfarina, que sí está). Escenarios concretos:
  - **Digoxina + Espironolactona o Furosemida** (ambas sí están en el dataset, pero solo emparejadas entre sí o con IECA — nunca con digoxina): hipopotasemia inducida por diurético potencia la toxicidad digitálica → arritmia. El hospital dispensa los tres fármacos; cero alerta posible.
  - **Metotrexato + Ibuprofeno o Diclofenaco** (ambos AINE sí están en el dataset): los AINE reducen el aclaramiento renal de metotrexato → mielosupresión y toxicidad renal severa, interacción clásica y bien descrita. El hospital dispensa los tres; cero alerta posible.
  - **Cloruro de potasio IV + Espironolactona/Enalapril/Losartán** (los tres sí están en el dataset entre sí, pero el dataset no tiene entrada alguna con cloruro de potasio, medicamento de alta alerta ISMP por definición): hiperpotasemia severa, riesgo de paro cardíaco. El hospital dispensa cloruro de potasio; cero alerta posible.
  - **Quetiapina + Azitromicina o Amiodarona** (ambas ya cubiertas por prolongación de QT con otros fármacos en el dataset): riesgo de torsades de pointes. El hospital dispensa quetiapina; cero alerta posible.
- **Consecuencia:** un médico que confía en que "si el sistema no avisa, es porque no hay interacción" está peor protegido que uno que sabe que no hay verificación en absoluto — es la falsa seguridad que la tarea de evaluación pidió explícitamente evitar.
- **Norma aplicable:** `TDR_HIS_Multipais.md` §7.4 y §15.3 (interacciones medicamento-medicamento con base de conocimiento integrada, dosis máximas, ajuste renal/hepático — ver H-04).
- **Naturaleza:** falta de datos/alcance del dataset, no defecto de la lógica que lo consulta (esa lógica funciona correctamente contra lo que sí carga).
- **Recomendación:** ver §5 (opciones) más abajo — la decisión de licenciar corresponde a dirección médica y a Edwin, no a este informe.
- **Evidencia:** consulta SQL contra `ServicePriceListItem`/`ServiceCategory` en producción (2026-08-22); conteo del dataset vía script Node sobre `drug-interactions.json`.

### H-04 · No hay verificación de duplicidad terapéutica, ajuste renal/hepático, embarazo/lactancia ni dosis pediátrica — pese a que el motor de cálculo ya existe, sin conectar · **Alto**

- **Proceso/módulo:** `pharmacy.router.ts` / `packages/infrastructure/src/formula/engine.ts`.
- **Qué observé:** el `Drug` model (schema.prisma) no tiene columnas de categoría de embarazo, dosis pediátrica por peso, ni ajuste por función renal/hepática. El único cruce que hace el sistema es par-a-par por ATC contra el JSON estático; no hay duplicidad terapéutica (dos fármacos de la misma clase farmacológica), ni verificación contra la función renal del paciente. Verifiqué que existe un motor de fórmulas clínicas con Cockcroft-Gault (`packages/infrastructure/src/formula/engine.ts`, con tests golden) — pero grep confirma que **nada fuera de `packages/infrastructure` lo importa**: no está conectado a ningún router ni a la prescripción.
- **Consecuencia clínica concreta:** un paciente de 78 años con creatinina elevada al que se le prescribe metformina o un AINE a dosis estándar sin ajuste renal — la insuficiencia renal es de las causas más comunes de eventos adversos evitables por medicación en adultos mayores, y el sistema no tiene ningún mecanismo, ni siquiera manual, para exponerlo en el punto de prescripción.
- **Norma aplicable:** `TDR_HIS_Multipais.md` §7.4 ("Dosis en insuficiencia renal y hepática", "Dosis pediátrica por peso/superficie corporal", "Categoría de embarazo... y lactancia") y §15.3 ("Ajuste por función renal (TFG) y hepática", "Interacciones con embarazo/lactancia", "Edad pediátrica/geriátrica") — brecha contractual directa, no interpretación.
- **Naturaleza:** defecto de alcance del diseño (el motor de cálculo existe pero no se integró) — no es solo falta de datos.
- **Recomendación:** priorizar conectar `formula/engine.ts` (Cockcroft-Gault) a un chequeo de alerta renal en `prescription.sign`, aunque sea como advertencia no bloqueante inicialmente, antes de sumar más pares de interacción al dataset — es una brecha contractual más amplia que R06 y con más pacientes en riesgo (todo adulto mayor con TFG reducida, no solo el subconjunto de pares de fármacos del dataset).
- **Evidencia:** `packages/database/prisma/schema.prisma` (modelo `Drug`, líneas 2059–2084, sin campos renal/hepático/embarazo/pediátrico); `grep -rn "formula/engine" packages apps` → 0 usos fuera de `packages/infrastructure`.

### H-05 · El catálogo ampliado con LASA/alto riesgo/doble custodia ya está modelado en BD pero tiene 0 filas y no está enlazado a `Drug` · **Alto**

- **Proceso/módulo:** `CatalogoMedicamento` (BD producción).

El documento JCI está desactualizado en el diagnóstico técnico, aunque la conclusión de "brecha abierta" sigue siendo correcta.
- **Consecuencia:** el trabajo de modelado (probablemente costoso: MDM golden id, mapeo SRS, Beers, LASA) existe y no está usándose para nada — ni para prescribir, ni para dispensar, ni para trazabilidad GS1 más allá de `ece.gs1_gtin`.
- **Norma aplicable:** IPSG.3 (lista codificada de medicamentos de alto riesgo, LASA) — ver `docs/32_gap_jci_assessment.md` línea 73-83, con la corrección de diagnóstico anotada arriba.
- **Naturaleza:** falta de carga de datos (backfill/seed pendiente), no defecto de diseño — clasificación importante para no pedirle a @Dev que rediseñe algo que ya está bien diseñado.
- **Recomendación:** antes de licenciar cualquier fuente comercial, cuantificar qué falta poblar en `CatalogoMedicamento` desde SRS (registro sanitario, ya integrado en modo lectura per memoria del proyecto) y desde el propio tarifario Odoo (1,897 productos). Puede que buena parte de la brecha de "catálogo clínico" se resuelva con carga de datos sobre un modelo que ya existe, antes de pagar una licencia.
- **Evidencia:** `\d "CatalogoMedicamento"` en producción (2026-08-22); `SELECT count(*) FROM "CatalogoMedicamento"` = 0; `SELECT count(*) FROM "Drug"` = 0; `docs/32_gap_jci_assessment.md` líneas 73-83.

### H-06 · El override de una interacción mayor no exige segunda firma ni restringe por rol · **Medio**

- **Proceso/módulo:** `pharmacy.prescription.sign` (`forceOverrideJustification`).
- **Qué observé:** para sobrepasar una interacción `major`/`contraindicated`, el único requisito es un texto libre de mínimo 10 caracteres (`forceOverrideJustification`), aportado por el mismo usuario que firma. El procedimiento usa `tenantProcedure`, no `requireRole([...])` — no hay restricción de rol server-side sobre quién puede firmar ni quién puede sobrepasar la alerta. Contraste: el mismo router sí exige `witnessUserId` distinto del dispensador + justificación para fármacos `RX_CONTROLLED` en `dispense.create` (2-eyes real). El override de interacción no tiene ese segundo control.
- **Consecuencia:** si este mecanismo se cablea a la UI (ver H-02), un solo usuario podría sobrepasar una alerta de warfarina+AINE o de QT largo sin que nadie más lo revise en el momento — el registro queda (evento `drug.interaction`, `notes` de la receta), pero es auditoría posterior, no control preventivo. Es menos grave que H-01/H-02 porque hoy es inalcanzable desde la UI, pero es un defecto de diseño que quedaría vigente el día que se cablee.
- **Norma aplicable:** IPSG.3 doble verificación para medicamentos de alto riesgo (ver `docs/32_gap_jci_assessment.md` línea 80: "Doble verificación independiente... BCMA es single-check, no double-check" — mismo patrón aquí, en prescripción en vez de administración).
- **Naturaleza:** defecto de diseño (menor prioridad que H-01/H-02/H-04, dado que hoy no es explotable desde la UI).
- **Recomendación:** cuando se resuelva H-02, exigir segunda firma (médico distinto o farmacéutico clínico) para overrides de severidad `major`/`contraindicated`, análoga al patrón 2-eyes ya implementado para `RX_CONTROLLED`.
- **Evidencia:** `pharmacy.router.ts` líneas 272-345 (sin `requireRole`); comparar con líneas 434-454 (`RX_CONTROLLED` sí exige `witnessUserId` + `controlledJustification`).

## Lo que el sistema hace bien

- **El hard-stop, donde se ejecuta, está bien diseñado.** El código de `prescription.sign` bloquea correctamente `major`/`contraindicated`, exige justificación mínima para override, y emite un evento de dominio `drug.interaction` con severidad (`CRITICAL`/`WARNING`) que queda en la cadena de auditoría (`AuditLog` con hash chain) — la trazabilidad del acto, cuando ocurre, es sólida. Confirmé cobertura de tests unitarios reales (no solo mockeados de forma que pasen en falso): `pharmacy.router.test.ts` cubre bloqueo por `major`, permiso con override, no-bloqueo por `moderate`/`minor`, y emisión de evento — 12+ casos específicos del mecanismo Beta.2.
- **Doble custodia real para fármacos controlados.** `dispense.create` exige `witnessUserId` distinto del dispensador + justificación para `RX_CONTROLLED`, y además lo exige (sin justificación obligatoria) para cualquier fármaco de alto riesgo ISMP por prefijo ATC (`isHighRiskAtc`) — esto sí es un control 2-eyes genuino, mejor que el override de interacciones (H-06).
- **Validación de lote/vencimiento en dispensación (FEFO).** `validateLotForDispense` bloquea dispensar lotes expirados o sin fecha de vencimiento — control de seguridad real e independiente del dataset de interacciones.
- **El diseño de `CatalogoMedicamento` anticipa correctamente lo que hace falta.** LASA, Beers, alto riesgo, doble custodia, EML OMS/LOM SV — es un modelo de datos maduro y alineado con estándares reales (ISMP, Beers Criteria, WHO EML). El trabajo pendiente es de carga y conexión, no de diseño desde cero.
- **Lo que el dataset sí cubre está bien elegido clínicamente.** El 92% de las sustancias mencionadas en las 50 reglas corresponden a productos que el hospital efectivamente factura — no es una lista genérica copiada sin criterio; prioriza anticoagulantes, prolongación de QT y síndrome serotoninérgico, que son clases de alto impacto real.

## Recomendación — dirigida a dirección médica

La pregunta que R06 plantea no es "¿el dataset de 50 pares es suficiente?" — no lo es, pero eso es lo de menos. La pregunta real es: **hoy, si un médico de este hospital prescribe dos medicamentos peligrosos juntos, ningún sistema se entera**, porque el módulo que sí verifica interacciones no es el módulo por el que se ordenan medicamentos en la práctica (H-01), y el módulo que sí lo verificaría no tiene ni un botón para activarlo (H-02). Eso no se arregla comprando Lexicomp o Vademécum — comprar una base de datos mejor y conectarla al lugar equivocado deja exactamente el mismo riesgo, con una factura de licencia encima.

Mi recomendación en tres pasos, en orden:

1. **Decisión de arquitectura clínica, no de compra (semanas, no dinero):** dirección médica y el equipo técnico deben decidir cuál es *el* punto único donde un médico ordena un medicamento en este hospital — indicaciones médicas NTEC (ya en uso operativo) o el módulo de Farmacia (con state machine y hard-stop, pero sin uso real ni UI de firma). Mientras haya dos, cualquier control de seguridad que se instale solo protege la mitad del problema.
2. **Con esa decisión tomada, sí recomiendo licenciar una fuente farmacológica especializada** (ver opciones abajo) — pero como insumo del punto único de prescripción, no como reemplazo aislado del JSON actual. Un dataset de 50,000 pares conectado al lugar equivocado vale lo mismo que uno de 50: cero.
3. **Mientras tanto, control compensatorio explícito y con dueño:** si el go-live de cualquier expansión del módulo de farmacia no puede esperar a la decisión de arquitectura, la verificación de interacciones para medicamentos de alto riesgo (digoxina, potasio, opioides, metotrexato, anticoagulantes) debe quedar en manos de doble verificación humana en el punto de dispensación —farmacéutico clínico revisando contra una referencia impresa o app comercial personal, documentado— hasta que el sistema la cubra. Ese riesgo residual, si se acepta transitoriamente, debe firmarlo dirección médica explícitamente (no el equipo de TI), porque es una decisión de seguridad del paciente, no de tecnología.

### Opciones de fuente farmacológica (para cuando se resuelva el punto 1)

| Fuente | Qué aporta | Consideración para El Salvador/LATAM |
|---|---|---|
| **Lexicomp (Wolters Kluwer) / Micromedex** | Estándar de referencia en muchos hospitales JCI; interacciones + dosis renal/hepática + embarazo/lactancia + pediatría, API integrable | Licencia comercial en USD, sin tarifa regional pública; es la opción que ya menciona el propio comentario del código (`Wave 2`) |
| **UpToDate Lexidrug (antes Lexicomp)** | Igual casa que arriba, integración con contenido clínico UpToDate si el hospital ya lo usa para consulta médica | Mismo costo/licencia; sinergia si hay suscripción UpToDate existente |
| **Vademécum (Vidal Vademecum Internacional)** | Fuerte en nomenclatura y presentaciones comerciales LATAM/España — mejor match con los nombres comerciales del tarifario actual (Odoo) que una fuente centrada en EE.UU. | Cobertura de interacciones más limitada que Lexicomp/Micromedex en algunas versiones; verificar API disponible vs. solo consulta web |
| **WHO EML + WHO ATC/DDD Index (pública, gratuita)** | Ya referenciada en el propio `CatalogoMedicamento.enEmlOms` — buena base de clasificación y de "qué es esencial", no una base de interacciones per se | No sustituye una base de interacciones; sirve para priorizar qué principios activos importa cubrir primero |
| **Listado SRS El Salvador (registro sanitario)** | Ya integrado en modo lectura en este proyecto (memoria de sesión: "SRS integración registro sanitario"); da identidad regulatoria local (`registroSrs`) | No es una base de interacciones — es la fuente de verdad de qué está registrado para venderse en el país, complementaria |
